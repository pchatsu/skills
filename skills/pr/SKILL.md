# プルリクエスト作成

プロジェクトの規約に従い、チケット番号付きタイトルとテンプレート化された説明でプルリクエストを作成する。

## ワークフロー

### 1. 現在の状態を分析

ブランチの状態を把握するため、以下のコマンドを並列実行:

```bash
# 現在のブランチとステータスを確認
git status
git branch --show-current

# リモート追跡ブランチの確認
git rev-parse --abbrev-ref @{upstream} 2>/dev/null || echo "No upstream"

# mainから分岐後のコミット一覧
git log main..HEAD --oneline

# PR説明用の差分を取得
git diff main...HEAD
```

### 2. タイトル形式の決定

タイトル形式: `簡潔な説明`（70文字以内）

- Issue 番号やチケット番号はタイトルに含めない
- Issue リンクは PR 本文の「Issue Link」セクションに記載する
- ブランチ名や コミットメッセージから Issue 番号を抽出し、本文に使用する

### 3. PR本文の生成

プロジェクトテンプレート `.github/pull_request_template.md` を使用:

```markdown
# Issue Link

- [URL]

# やった事

- このプルリクエストで何をしたのか？

## なぜやるのか

- Issue で説明できない捕捉的な事項 (Issue の説明で十分であればここは不要)

# Refs (コーディングにあたって参考にした情報）

- [URL]
```

テンプレートの埋め方:
- ブランチ内の全コミットを分析（最新だけでなく全て）
- 「やった事」セクションに変更内容を要約
- チケット番号が見つかればIssueリンクを追加
- 参照したドキュメントをRefsに記載

### 4. プッシュとPR作成

```bash
# アップストリーム追跡付きでブランチをプッシュ
git push -u origin $(git branch --show-current)

# HEREDOCで本文をフォーマットしてPR作成
gh pr create --title "簡潔なタイトル" --body "$(cat <<'EOF'
# Issue Link

- https://github.com/org/repo/issues/XXX

# やった事

- 変更内容の要約...

## なぜやるのか

- 必要に応じて追加のコンテキスト

# Refs (コーディングにあたって参考にした情報）

- 参照したドキュメント
EOF
)"
```

### 5. 結果の報告

完了後、PR URLをユーザーに返す。

## 重要なルール

- main/masterに直接プッシュしない
- 明示的に要求されない限り `--force` を使用しない
- gitフック（`--no-verify`）をスキップしない
- 正確なPR説明のためブランチ内の全コミットを分析する
- チケット番号が見つからない場合は続行前にユーザーに確認する
