# レスポンシブとビューポート

このスキルが出力する成果物には、大きく2つの形がある。**文書**（スクロールして読む1ページ）と**プレゼンテーション**（1画面1トピックの固定ビューポートスライド）。この2つはビューポートの扱い方がほぼ正反対になる。文書は画面幅に合わせて柔軟に振る舞い、スライドは画面幅を無視して固定サイズに収まる。両者を混同すると、文書がスライドのように窮屈になったり、スライドがレスポンシブに崩れて読めなくなったりする。

以下ではA. 文書、B. プレゼンテーションの順にルールを分けて説明する。

---

## A. 文書 — スクロールする読み物としての快適さ

文書はスマホでもタブレットでもデスクトップでも、同じ内容を無理なく読めること。目的はレイアウトの派手さではなく、可読性そのもの。

### 譲れないルール

出力は少なくとも **375px前後（スマホ）と1440px前後（デスクトップ）** の両方で目視確認する。余裕があれば320px・768pxも確認する。

- **横スクロールが発生しないこと。** ルート要素（`html` と `body` の両方）に `overflow-x: clip` を設定する。`hidden` は使わない（`hidden` はスクロール位置の計算やstickyな子要素の挙動を壊すことがある）。
- **画像・図表を含むグリッドがビューポート幅を超えて押し広げないこと。** 画像を含むトラックには裸の `1fr` ではなく `minmax(0, 1fr)` を使う。画像自体には `max-width: 100%; height: auto;` を必ず指定する。
- **長い単語・URL・識別子が横あふれを起こさないこと。** 見出し・本文とも `overflow-wrap: anywhere; min-width: 0` を設定する。特に日本語文書に英語の識別子（`getUserProfileById()` のような）が混ざるとき、コード以外の地の文でも折り返せるようにしておく。
- **コードブロックはページ全体を横に広げない。** `pre`/`code` は自身のコンテナ内で `overflow-x: auto` を持ち、ページ全体のスクロールには影響させない（詳細は後述）。

これは努力目標ではなく最低ラインである。1項目でも満たさなければ未完成として扱う。

### 読みやすい行長（measure）

長文の可読性を最も左右するのは行の長さである。1行が長すぎると読者は次の行の先頭を見失い、短すぎると視線の往復が増えて疲れる。

- 本文コンテナの最大幅は **60〜75文字相当**（英語なら `max-width: 65ch` 前後、日本語なら `max-width: 38em` 前後が目安）に収める。
- 本文の基準フォントサイズは **最低16px（1rem）**、行間は `line-height: 1.6〜1.75`。
- 段落間・見出し前後の余白は行間より明確に大きくし、セクションの切れ目を視覚的に示す。

```css
.doc-body {
  max-width: 42rem; /* ≈ 65ch 相当。フォントにより微調整 */
  margin-inline: auto;
  font-size: 1rem;
  line-height: 1.7;
}
```

幅の広いデスクトップ画面では、本文コンテナだけを中央寄せで固定してよい。本文をビューポート幅いっぱいに伸ばして1行150文字にしてしまうのが、最もよくある失敗である。

### 流体タイポグラフィ

見出しサイズなど連続的に変化させたいものには `clamp()` を使う。

```css
h1 { font-size: clamp(1.75rem, 3vw + 1rem, 3rem); }
.doc-container { padding-inline: clamp(1rem, 4vw, 3rem); }
```

### コードブロックの折り返し

- コードブロックは折り返さず `white-space: pre` を基本とし、横にはみ出す行はブロック自身が `overflow-x: auto` でスクロールする（ページはスクロールしない）。
- インラインコード（`` `code` ``）は地の文の中に置かれるため `overflow-wrap: anywhere` を効かせ、長い識別子でも行内で折り返せるようにする。
- スマホ幅ではコードブロックの横スクロールが発生しても構わない。ただし本文サイズよりコードのフォントを極端に小さくしない（最低13〜14px相当）。

### 表

収まらないデータテーブルは、そのままスマホに押し込まない。

- 列数が多い表は `<tr>` に `display: block` を指定してカード状に畳み、`<th>` から取得した `data-label` 属性を `::before` で表示する。
- あるいは、モバイル幅では表そのものを要点だけのリストや小さなカード群に作り替える。表はもともとモバイルに向いた表現ではないことが多い。

### 画像

- レスポンシブなサイズ指定には幅記述子付きの `srcset` を使う。
- ファーストビュー外の画像には `loading="lazy"` を使う。
- CLS（レイアウトのガタつき）を避けるため、すべての画像に常に `width` と `height` 属性を指定する。

### ビューポート単位とセーフエリア

- モバイルのブラウザUIと連動する高さには `vh` の代わりに `dvh` / `svh` / `lvh` を使う。
- `width: 100vw` は使わない。`width: 100%` とpaddingを使う（`100vw` はデスクトップのスクロールバー幅を含み、はみ出しの原因になる）。
- モバイルで読む前提の文書（PWA的な読書体験など）では、ノッチ対応のセーフエリアを確保する。

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

```css
body {
  padding-inline: max(1rem, env(safe-area-inset-left));
  padding-bottom: max(1rem, env(safe-area-inset-bottom));
}
```

### 国際化

- ドイツ語・ロシア語・フィンランド語などの翻訳のために、横方向の余白を30〜40%多めに確保する。
- `margin-left` 等ではなく論理プロパティ（`margin-inline-start`、`padding-block`、`border-inline-end`）を使う。RTLが自動的に対応する。
- 言語固有の句読点や日付形式をハードコードしない。

### 禁止事項（文書）

- `max-width: 768px` を主方向とするデスクトップファーストのメディアクエリ。
- フルハイトレイアウトでの `vh`（`dvh` を使う）。
- `100vw` 幅の指定。
- 本文コンテナをビューポート幅いっぱいに広げて行長を無制限にすること。
- `rem` を尊重しない固定ピクセルのブレークポイント。
- 再設計なしに10カラム以上のテーブルをモバイルに表示すること。

## B. プレゼンテーション — 固定ビューポートのスライド

スライドは文書と違い、通常は**レスポンシブにしない**。ビューポート幅に応じてレイアウトを組み替えるのではなく、**固定のアスペクト比・固定解像度のキャンバス**を設計し、それが実際の画面（プロジェクター、外部モニタ、ブラウザウィンドウ、PDF出力）にどう収まるかだけを制御する。ここを最初に取り違えると、要素の絶対配置が画面サイズごとに崩れる。

### 固定アスペクト比というキャンバス

標準は **16:9**。基準解像度として **1280×720** または **1920×1080** を1つ選び、以後すべてのスライドをそのpxグリッド上で設計する（`vw`/`vh` 単位で都度スケーリングするのではなく、固定px単位で絶対配置してよい——それがスライドの設計様式である）。

ブラウザウィンドウやプロジェクターの実解像度は基準解像度と一致しないので、**デッキ全体を一つのブロックとして均一スケーリング**して収める（レターボックス）。

```css
:root {
  --slide-w: 1280px;
  --slide-h: 720px;
}

.slide {
  width: var(--slide-w);
  height: var(--slide-h);
  flex: none;
  position: relative;
}

.deck-viewport {
  position: fixed;
  inset: 0;
  display: grid;
  place-items: center;
  background: #000; /* レターボックス部分の色 */
  overflow: hidden;
}

.deck {
  transform-origin: center center;
}
```

```js
function fitDeck() {
  const scale = Math.min(
    window.innerWidth / 1280,
    window.innerHeight / 720
  );
  deck.style.transform = `scale(${scale})`;
}
window.addEventListener("resize", fitDeck);
fitDeck();
```

JSを使わない純CSSの代替として、ブラウザ内プレゼン専用（PDF書き出しは別経路で対応）なら以下のレターボックストリックも使える。

```css
.slide {
  width: min(100vw, 100vh * 16 / 9);
  height: min(100vh, 100vw * 9 / 16);
  margin: auto;
}
```

どちらの方式でも、**個々の要素はビューポート単位ではなく基準解像度のpx単位で配置する**。`font-size: 2vw` のような指定は解像度が変わるたびに文字の相対比率が変わってしまう（見出しと本文の比率が壊れる）。デッキ全体をスケーリングし、中の値は固定pxのままにする。

### 可読性の最低基準

プロジェクターや大画面、会議室の後方席から読めることを基準にサイズを決める。デスクトップUIの感覚（本文14〜16px）はスライドには小さすぎる。

| 要素 | 最小サイズ（1280×720基準） |
| --- | --- |
| タイトル（表紙スライド） | 60〜96px |
| 見出し（セクション/スライドタイトル） | 40〜56px |
| 本文 | 28〜32px |
| 箇条書き | 24〜28px |
| キャプション・出典・脚注 | 20px以上（これ未満は「読めなくていい情報」として扱う） |
| コード | 24〜28px（等幅） |

1920×1080基準で作る場合は上記を1.5倍する。

**コントラストはWCAG AAより厳しく取る。** 本文は **APCA Lc 75以上**（会議室の照明・プロジェクターの発色劣化を見込んだ余裕）、見出しや大きな装飾文字でも Lc 60を下回らない。WCAG基準に換算するとおおむね本文7:1相当。デスクトップUIでは許容される、淡いグレーの本文＋白背景のような組み合わせは、スライドでは不合格になりやすい。

### 詰め込みすぎない設計

スライドがあふれる原因はフォントサイズの選択ミスではなく、**そもそも情報を詰め込みすぎている**ことがほとんどである。`overflow: hidden` で見切れさせて隠すのは対症療法であり、読者はその見えない部分の存在にすら気づけない。

- 1スライド1トピックを徹底する。伝えたいことが2つあるなら2枚に分ける。
- 本文の目安は **1スライドあたり40〜60語（日本語なら100〜150字）以内**、箇条書きは **5〜6行以内**。それを超える原稿が来たら、削るか分割するかをまず検討する。
- 見出し・本文とも `overflow-wrap: anywhere; min-width: 0` は文書と同様に効かせておく（長い固有名詞や識別子の対策として）。ただしこれは事故対策であり、詰め込み過多を許容する言い訳にしない。

`clamp()` によるフォント自動縮小（コンテンツ量に応じて本文を28pxから20pxまで自動で縮める、など）は**最後の安全網としてのみ**使う。主戦略にはしない。自動縮小は、文字が小さくなったことを作者に知らせないまま、気づかないうちに可読性の最低基準を割り込ませてしまう。後方の座席で読めないスライドが生まれる典型的な原因である。使うとしても下限は可読ラインより下げない。

```css
/* 安全網としてのみ。下限28pxを下回らせない */
.slide__body {
  font-size: clamp(1.75rem, 1vw + 1.4rem, 2rem);
}
```

あふれが起きたら、まずコピーを削るか2枚に割ることを検討する。フォントを縮めることも `overflow: hidden` で隠すことも、最終手段として扱う。

### 印刷／PDF書き出し

多くの場合、作成したスライドはブラウザの印刷機能でPDF化される。スライド1枚＝印刷1ページになるよう明示的に制御する。

```css
@media print {
  @page {
    size: landscape; /* もしくは基準解像度に合わせた実寸: 13.333in 7.5in など */
    margin: 0;
  }

  html, body {
    print-color-adjust: exact;
    -webkit-print-color-adjust: exact; /* 背景色・アクセントカラーを印刷で消さない */
  }

  .deck-viewport {
    position: static;
    background: none;
  }

  .deck {
    transform: none !important; /* 画面用のスケーリングを解除し等倍で出力する */
  }

  .slide {
    width: 100%;
    height: 100vh;
    break-after: page;
    break-inside: avoid;
  }

  .slide:last-child {
    break-after: auto;
  }

  /* 画面専用のナビゲーションUIは印刷しない */
  .deck-nav,
  .progress-indicator,
  .slide-controls {
    display: none !important;
  }
}
```

`print-color-adjust: exact` を忘れると、暗い背景のスライドが印刷時に真っ白になり、白文字が消えて読めなくなる。背景色・アクセントカラーを使うデッキでは必須。

### スライドナビゲーション

- **キーボード操作。** 右矢印キー／スペースキーで次のスライド、左矢印キーで前のスライドへ。Home/Endキーで最初/最後へ飛べると尚良い。
- **URLフラグメントで位置を保持する。** `#3` のようにスライド番号をハッシュに反映し、リロードや共有リンクで同じスライドから再開できるようにする。
- **進捗インジケーター。** 「3 / 24」のようなテキスト、または現在位置を示すドット列・細い進捗バーのいずれかを常時表示する。
- **端での無効化。** 最初のスライドで「前へ」、最後のスライドで「次へ」を `disabled` にする。ボタンを消したり非表示にしたりはせず、無効状態として見せる（状態遷移でレイアウトが動かないようにするため。詳細は [`interaction-and-states.md`](interaction-and-states.md)）。

```js
const slides = document.querySelectorAll(".slide");
let current = Math.min(
  Math.max(Number(location.hash.slice(1)) || 0, 0),
  slides.length - 1
);

function goTo(i) {
  current = Math.max(0, Math.min(slides.length - 1, i));
  render();
  history.replaceState(null, "", `#${current}`);
}

function render() {
  slides.forEach((s, i) => s.toggleAttribute("hidden", i !== current));
  prevBtn.disabled = current === 0;
  nextBtn.disabled = current === slides.length - 1;
  progress.textContent = `${current + 1} / ${slides.length}`;
}

document.addEventListener("keydown", (e) => {
  if (e.key === "ArrowRight" || e.key === " ") { e.preventDefault(); goTo(current + 1); }
  if (e.key === "ArrowLeft") goTo(current - 1);
  if (e.key === "Home") goTo(0);
  if (e.key === "End") goTo(slides.length - 1);
});

render();
```

### 禁止事項（プレゼンテーション）

- 見出しや本文サイズを `vw` だけで指定すること（解像度ごとに比率が壊れる）。デッキ全体のスケーリングと、中身の固定px指定を分離する。
- `overflow: hidden` だけであふれを解決すること。まずcontentを削るか分割する。
- WCAG AA基準ぎりぎりのコントラストで妥協すること。スライドはAAAに近い基準で作る。
- 印刷時に `print-color-adjust` を設定せず、背景色が消えるまま出荷すること。
- スライドナビゲーションをマウスクリックのみに依存させ、キーボード操作を提供しないこと。
