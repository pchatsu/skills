# 図解

この資料は、文書やスライドの中でMermaidのような軽量記法を使って図解（フローチャート・比較・タイムラインなど）を作るときの規律をまとめたものだ。狙いは一つ——Mermaidのデフォルトの見た目（紫/青のグラデーション、不揃いなノードサイズ、汎用フォント）をそのまま出力して、「いかにもAIが生成した図」に見えてしまう事態を避けること。[`structure.md`](structure.md) の「図解とテキストの比率」と対になる資料であり、判断はまず「そもそも図が必要か」を疑うところから始める。

## 1. そもそも図解が必要か

図にすること自体はゴールではない。「文章や表より速く伝わる」ことがゴールだ。次の表で、扱おうとしている情報の性質と照合する。

| 情報の性質 | 図解が必要か | 代替 |
| --- | --- | --- |
| 3列以下×5行以内の比較 | 不要 | 素のHTML `<table>` |
| 分岐のない4〜5点以内の時系列 | 不要 | 日付＋説明の箇条書き |
| 2〜3ステップの単純な手順 | 不要 | 番号付きリスト |
| 分岐・条件分岐・並行するプロセスがある手順 | 必要 | flowchart |
| 役割間のメッセージのやり取り、時系列の相互作用 | 必要 | sequence diagram |
| 6個超のノード間の依存関係・階層構造 | 必要 | flowchart / 階層図 |
| 概念的・比喩的な説明（仕組みを絵で直感的に見せたい） | 場合による | 手組みSVG/CSSも検討（6章） |

表で済む比較情報を、無理にflowchartのノードと矢印に変換すると、かえって読み取りに時間がかかり、しかも見た目のAI感が増す。迷ったら「表 → 箇条書き → 図解」の順で、より軽い手段で足りないかを先に確認してから図解に進む。

## 2. Mermaidを使うと決めたら——スタイリング規律

デフォルトテーマ（`theme` を指定しない、または `theme: 'default'`）のまま出力しない。これがMermaid図が安っぽく見える最大の原因——紫系の `primaryColor`、既定のsans-serif、太さの揃わない枠線がそのまま出てしまう。

必ず `%%{init: {...}}%%` ディレクティブで `theme: 'base'` を指定し、`themeVariables` をページの配色トークン（OKLCHベースの `--color-*`）とフォントトークンに合わせて上書きする。

```
%%{init: {
  "theme": "base",
  "themeVariables": {
    "primaryColor": "#F4ECDF",
    "primaryTextColor": "#231F1A",
    "primaryBorderColor": "#B65C2E",
    "lineColor": "#8C8172",
    "secondaryColor": "#E7DCC8",
    "tertiaryColor": "#FBF7EF",
    "fontFamily": "Geist, ui-sans-serif, system-ui, sans-serif",
    "fontSize": "16px"
  }
}}%%
graph LR
  A[会員登録] --> B{メール確認済み?}
  B -->|はい| C[ダッシュボードへ]
  B -->|いいえ| D[確認メール再送]
```

値は生の16進カラーで指定しているが、これはページの `--color-paper-2`・`--color-ink`・`--color-accent`・`--color-rule` と同じ色相・明度になるよう手元で対応させたものだ。MermaidのSVG出力は環境によって `oklch()` 関数の解釈が不安定なため、トークンの値を一度16進に変換してから `themeVariables` に渡す。値の由来が追えるよう、コメントで元のトークン名を残しておく（例：`"primaryColor": "#F4ECDF" /* = --color-paper-2 */`）。

規律としてまとめると：

- **`fontFamily` はページの `--font-body` または `--font-mono` と同じ書体名を指定する。** Mermaid既定の `"trebuchet ms", verdana, arial` を残さない。
- **`forest` / `dark` / `neutral` といった既定のプリセットテーマもそのまま使わない。** これらもまた「既定テーマの顔」をしている。`base` テーマを起点に、`themeVariables` で独自に配色する。
- **ノードの形状は意味に応じて統一する。** 開始・終了は角丸（`([...])`）、通常の処理は矩形、分岐は菱形（`{...}`）。同じ役割のノードに異なる形状を混在させない。装飾目的だけで形状を変えない。

## 3. 図の複雑さの上限

- **ノード数の目安は1図あたり7〜9個、上限12個。** 人が一度に保持できる要素数に対応させた目安であり、これを超えると読み手は図の全体像を追えなくなる。
- **分岐（菱形ノード）の連続は2〜3段まで。** それ以上分岐が続く場合、1つの図に複数の意思決定プロセスを詰め込んでいるサインになる。
- **分割の判断。** ノード数が上限を超えた、あるいは通常のビューポートでスクロールやピンチズームをしないと読めない場合は、(a) 全体像を示す粗い図（5〜6ノード）と、工程ごとの詳細図に分ける、(b) そもそも関係性が表形式（属性同士の比較）であれば表に戻す、のいずれかを選ぶ。文字サイズを縮めて1枚に収めようとしない。

## 4. ノード内テキストの規律

- ノードラベルは体言止め、目安4〜6語（日本語で12〜16文字）以内に収める。
- 「〜のときに送信されます。」のような完結した文をノードに入れない。文で説明が必要な情報は、図の前後のキャプションに逃がす。
- 改行が必要な場合は `<br/>` で意味のまとまりごとに切る。1ノード内は最大2行までとし、3行目に達しそうならラベルそのものを短縮する。
- 同じ図の中でラベルの文法形式を揃える。名詞句で統一するか動詞句で統一するかを決め、「ユーザー登録」（名詞句）の隣に「メールを送信します」（文）のような異なる形式を混在させない。

## 5. 矢印・エッジの一貫性

- 1つの図の中で矢印の種類を無闇に混在させない。実線 `-->` は確定した流れ、破線 `-.->` は条件付き/任意の経路、太線 `==>` は強調したい主経路、というように意味を固定してから使い分ける。意味の違いがないなら実線1種類で統一する。
- エッジラベルは分岐の条件（「はい」「いいえ」「該当あり」など）のように、判断に必要な情報にだけ使う。自明な遷移にまでラベルを付けない。
- **レイアウト方向は交差の少なさで選ぶ。** 左→右に読ませたい直線的なプロセス（申込→承認→発行のような一本道）は `graph LR`。階層・組織図・意思決定ツリーのように上下関係が意味を持つ図は `graph TD`。`TD` で幅広の図を作ると線の交差が増えやすいので、その場合は `LR` に倒すか、`subgraph` で関連ノードをクラスタ化して交差を減らす。

## 6. アクセシビリティ

図の直前直後に、視覚に依存しない短い説明文を添える。加えて、Mermaid記法自体にも `accTitle` / `accDescr` ディレクティブで要旨を埋め込む。

```
graph TD
  accTitle: 会員登録フロー
  accDescr: メールアドレスを入力し、確認メールのリンクをクリックすると登録が完了する3ステップのフロー
  A[メールアドレス入力] --> B[確認メール送信]
  B --> C[リンクをクリックして登録完了]
```

`accDescr` はスクリーンリーダー専用で、画面には表示されない。晴眼の読者にも同じ要旨が伝わるよう、目に見えるキャプション（`<figcaption>` や図の直後の一文）も併せて用意する。

## 7. Mermaid以外の選択肢

込み入った概念図・比喩的な図解には向かないことがある——仕組みそのものを絵解きしたい、実体のない関係性を空間的に見せたい、といった場合だ。そのときはMermaidのノード語彙（矩形・菱形・矢印）に無理に押し込めるより、手組みのインラインSVG/CSSで自由な形状・レイアウトを使う方が誠実になる。Mermaidが向いているのは「構造化された関係」を描くことで、「感覚的な比喩」を描くことには向いていない。ここでは方向性の指摘にとどめ、作成の詳細な規律には立ち入らない。

## 8. 図解のスロップチェックリスト

出力前に確認する。

1. デフォルトテーマ（紫系の `primaryColor`、既定フォント）のまま出していないか。
2. ノードや線の色は、ページの `--color-*` トークンと対応が取れているか（その場しのぎの色になっていないか）。
3. フォントは `--font-body` / `--font-mono` と一致しているか（Mermaid既定のTrebuchet MSが残っていないか）。
4. ノード数は7〜9個（上限12個）に収まっているか。超えているなら分割を検討したか。
5. 矢印の種類・エッジラベルの付け方は図全体で一貫しているか。
6. 交差する線が目立たないレイアウト方向（`LR` / `TD`）を選んだか。
7. `accTitle` / `accDescr`、または目に見えるキャプションを添えたか。
8. 表や箇条書きで足りる情報を、無理に図解にしていないか。
