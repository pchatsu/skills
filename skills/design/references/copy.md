# コピー

言葉はデザインの一部だ。優れたレイアウトに紋切り型のコピーを乗せると陳腐に見える。平凡なレイアウトでも、言葉が締まっていれば「考え抜かれている」と読める。理解ノートでもレポートでもスライドでも、この関係は変わらない。

## 原則

- **動詞は具体的に。** 「対応する」「行う」より「減らす」「防ぐ」「置き換える」のような、何が起きるかが一語で伝わる動詞を選ぶ。
- **簡潔に書く。フィラー語を削る。** 「基本的に」「そもそも」「言うまでもなく」「〜することができます」のような、意味を運ばない語句を削る。一文一義。
- **見出し・ラベル・リンクテキストは単独で意味が通るようにする。** 前後を読まなくても、その一語・一文だけで何を指すか分かるようにする。
- **能動態。** 「原因は特定できなかった」ではなく「原因を特定できなかった」。主語を隠さない。
- **一貫性。** 同じ概念には同じ語を使う。「削除」と「消去」を混在させない。文書やデッキ全体で用語集を1つに保つ。

## 誠実なコピー — 数値・データ・引用を捏造しない

これは全原則の中でもっとも重要である。理解ノート・レポート・スライドはいずれも事実を運ぶための媒体であり、そこに書かれた数字や引用は「本当にそうである」という信頼のもとに読まれる。

- **ユーザーから与えられていない数字を生成しない。** 「30%改善」「主要企業の80%が導入」「稼働率99.9%」のような、もっともらしいが出典のない統計をでっち上げてはならない。これはボタンやヒーローの実績バーだけの問題ではなく、レポートの本文、スライドの統計スライド、グラフの数値ラベルすべてに当てはまる。
- **実データがない場合の扱いは3通り。** (1) プレースホルダーを明示する（「[要確認: 実際の数値]」「出典: 未定」）。(2) ユーザーに実数を尋ね、確認が取れるまで作業を止める。(3) 数字前提の構成自体をやめ、定性的な説明に置き換える。空欄のままにするのは誠実だが、数字を捏造するのは誠実ではない。
- **引用は出典を明記できるものだけを書く。** 誰の発言か分からない気の利いた一文を、権威付けのために文書やスライドへ差し込まない。
- **グラフ・表のサンプルデータには、それがサンプルであることを明示する。** 「サンプルデータ」「架空の数値（イメージ）」のようなラベルを添え、実データと誤認されないようにする。
- 数字を主語にした見出し（「23拠点 · 4部門 · 従業員482名」のような型）は説得力が強い分、捏造のダメージも大きい。使うなら実数のときだけ使う。

## 見出し・スライドタイトルの書き方

- **1スライド1メッセージ。** タイトルはそのスライドの結論そのものを言う。トピック名（「売上」）ではなく主張（「売上は第2四半期に前期比で減少」）にする。
- **短く、遠くから読める長さに。** 日本語なら目安20〜24字、英語なら7語程度まで。1行に収まらないタイトルは、たいてい2つのメッセージを1枚に詰め込んでいる。
- **体言止めか動詞止めかを、文書・デッキ全体で統一する。** 「導入手順」（体言止め）と「手順を導入する」（動詞止め）を混在させない。どちらを選ぶかより、選んだ後に一貫させることの方が重要。
- **長文ドキュメントの見出しは目次に単独で現れる。** 「概要」のような曖昧な見出しを乱用せず、内容を予告する名詞句にする（「概要」より「対象範囲と前提」）。

## 長文ドキュメントの導入部

- 最初の3〜5行で「これは何についての文書か」「誰向けか」「読むと何が分かるか」を明らかにする。読者は本文を読み進めるかどうかを冒頭だけで判断する。
- 「〜という時代において」のような前置きの美辞麗句で始めない。結論やスコープから始める。
- 目次を置く場合は導入部の直後に配置し、見出し文言と完全一致させる。

## コールアウト／補足ボックスの文体

- ラベルは中身の性質を一語で示す（注 / 補足 / 例 / 警告 / 引用など）。
- 本文の論の流れを止めずに読み切れる、独立した1〜3文で書く。ボックスの中で新しい話題を始めない。
- 装飾のためのボックスを作らない。地の文で十分な内容をわざわざ枠で囲むと、かえって「ここだけ生成された挿入物」のように浮く。

## 正しいタイポグラフィ

- カーリークォート: `"Hello"`、`'word'`。
- 中断を表すエムダッシュ: `—`（U+2014）。範囲を表すエンダッシュ: `10–20`（U+2013）。`--` は使わない。
- 三点リーダー: `…`（U+2026）。`...` は使わない。
- アポストロフィ: `’`。プライム記号 `'` は使わない。
- 単位の前のノーブレークスペース: `10 kg`、`5 min`（`&nbsp;` または U+00A0 を使う）。

CMSからテキストを読み込む場合はCMS側でスマートクォートを設定する。ハードコードする場合は最初から正しく書く。

## 具体性のパターン集

AI生成コピーは、放っておくとありきたりな表現に寄っていく（「Built for the modern team」「Unleash your X」「Where A meets B」など）。それを避けているコピーには共通のパターンがある。**真似るべきは具体性の"種類"** ——固有の場所・日付・業種名、比喩を使わないこと、動詞そのものを削ること——であって、言い回しをそのまま借りることではない。

代表的なパターン:

- **日付/場所アンカー型。** 「Creative direction, design and type for culture since 2003.」— 年号や地名を入れると急に嘘のつけない具体性が生まれる。
- **動詞拒否型。** 「A thing well made.」「Writer + Photographer.」— 動詞を削るほど、言い切りの強度が増す。
- **平叙文型（誇張なし）。** 「The product development system for teams and agents.」— 誰向けか・何をするかを飾りなく言う。
- **数字を主語にする型。** 「23 spans · 4 services · 482 ms.」「23 partners work independently…」— 具体的な数字そのものが見出しになる。ただし前節のとおり、実数がある場合に限る。
- **拒否による定義型。** 「We are a studio. We are not a platform.」— 何であるかより、何でないかを言う方が輪郭が立つことがある。
- **列挙型。** 「Typography, motion design, copywriting, performance — the web is an endless medium of opportunity.」— 熱意を機能の列挙で示す。

ブリーフに具体性の材料が何もない場合は、無理に発明せず一つ質問して具体的な名詞・動詞・場所を引き出す。ユーザーは自社の題材を知っている。モデルが具体性を捏造してはならない。

## 禁止されるオープニング行（アンチパターン）

以下のフレーズはAI生成コピーに頻出し、上記のような具体性を一切持たない。**使用禁止。** これらに手が伸びたら、上のパターンのいずれかに置き換える。

| フレーズ | 何がダメか |
| --- | --- |
| *"Built for the modern team"* | 曖昧。具体性ゼロを前提にした時流迎合表現 |
| *"Unleash your [X]"* | 誇大。ソフトウェアは何かを「解き放つ」ことはできない |
| *"Where X meets Y"* | 偽の統合。安易な創造性の欠如 |
| *"Empower your..."* | 布教的な言葉。具体的な便益を避けている |
| *"Reimagine the way you..."* | 説明する前に不満を前提としてしまう |
| *"Supercharge your workflow"* | 仕組みの説明を伴わないエネルギー比喩 |
| *"Innovative solutions"* | 無意味。あらゆる製品が革新を謳う |
| *"Seamless integration"* | 「Seamless」には対義語がなく、非具体性のサイン |
| *"In today's digital landscape"* | 時流への言い訳。読者に前置きが必要だという思い込み |
| *"Next-generation"* | 前世代が不十分だったことを暗示するだけで、差別化を何も示さない |

## Webアプリのコピー（参考）

ボタンラベルやフォームのエラーメッセージなど、インタラクティブなWebアプリ特有のコピーを書くときは、次の原則を当てはめれば十分だ。

- ボタンは実行するアクションの動詞を使う（「OK」より「変更を保存」）。
- エラーは「何が起きたか → なぜか → どうすればよいか」の順で、事実ベース・命令形に書く。ユーザーの入力に謝罪的な態度を取らない（「Oops!」を使わない）。
- 「Click here」のようなリンクテキストは避ける——上の「見出し・ラベル・リンクテキストは単独で意味が通るようにする」原則がそのまま適用される。
