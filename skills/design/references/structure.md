# 構造

このファイルは、Webページ（ランディングページ）のマクロ構造カタログではない。このスキルが主に扱う2つの成果物 —— **文書**（スクロールする1ページの長文HTML。自分用の理解ノート、または共有用の資料）と **スライド**（1画面=1トピックのプレゼンテーション、16:9固定ビューポート想定）—— を組み立てるときに考えるべき構造の軸をまとめている。ヒーロー・ナビゲーション・フッター・CTA・価格表・テスティモニアルといったLPの語彙はここには出てこない。代わりに扱うのは、見出しの効かせ方、読者が迷わないための手がかり、区切りのリズム、図とテキストの配分、スライドとスライドの間の呼吸といった、読み物や語りの資料に固有の判断軸だ。

文書とスライドは、同じ内容から作るとしても組み立て方が別物だ。文書は読者が自分のペースでスクロールし、前後を行きつ戻りつしながら読む。スライドは話者が場を仕切り、聴衆は1画面ずつ、話速に合わせて情報を受け取る。この体験の違いがそのまま構造の違いになる。

## 文書かスライドか

依頼の言葉から、どちらを作るべきかを最初に見極める。

| 手がかり | 文書 | スライド |
| --- | --- | --- |
| 「まとめて」「整理して」「理解ノート」「メモ」 | ○ | |
| 「発表資料」「説明する」「人前で話す」「デッキ」 | | ○ |
| 読者が自分のペースで読み進める想定 | ○ | |
| 話者が口頭で補足しながら進める想定 | | ○ |
| 情報量が多く、後から検索・参照される | ○ | |
| 1画面ごとに視線を誘導し、話の流れを作る | | ○ |

判断がつかない場合は一つだけ尋ねる。「これは後で読み返す資料ですか、それとも人前で話しながら見せる資料ですか？」

## 文書の構造軸

### 1. 見出し階層とスキャン性

- H1は文書タイトルのみに使い、1つに限定する。
- H2は主要セクション。目安として1,200〜2,000語に1つ程度のペースで置く。
- H3はH2の下位トピック。H4は表内の小見出しなど限定的な場面でのみ使い、常用しない。
- 見出しレベルを飛ばさない（H2の次に直接H4を置かない）。見た目の大きさは自由に調整してよいが、文書構造（アウトライン）は必ず順番通りにする。
- **目次（TOC）を付けるかどうかの判断基準。** 次のいずれかに当てはまればTOCを付ける：H2が4個以上ある、想定読了時間が7〜8分（概ね1,800語）を超える、読者が頭から通読せず目次から目的のセクションへ直接ジャンプする使い方（リファレンス的な参照）が想定される。逆に、H2が3個以下の短い文書や、頭から通読させたいナラティブ主体の文書ではTOCを省いてよい。TOCには便利さと引き換えに「もう全部は読まなくていい」という離脱の合図になる面もある——長さに見合わない文書に、反射的にTOCを付けない。
- **長い文書での現在地の手がかり。** 3,000語を超える文書では、読者が「今どこを読んでいるか」を見失いやすくなる。対策の候補：スクロールに応じて現在のH2をハイライトするミニTOC（サイドまたはスティッキーヘッダー）、「セクション3/6」のような進捗表示、あるいは単に十分な余白とセクション番号で視覚的な区切りを強くする。短い文書ではこれらの装置自体が過剰装飾になるため、必要になった文書だけに足す。

### 2. セクションのペース配分

情報の密度は大きく二極に分けて考える。混ぜるなら意図的に混ぜる。

- **リファレンス的密度。** 情報/ピクセル比を高く保つ。表・箇条書き・コードブロックを多用し、余白は必要最小限。API文書、チートシート、社内Wiki的な理解ノートに向く。
- **エディトリアル的密度。** 段落間・セクション間に大きめの余白を取り、1つの主張を1つの画面で語らせる。長めの導入文や物語的な接続を許容する。エッセイ的な共有文書、意思決定の背景を説明する文書に向く。

1つの文書内では密度を統一する。前半が余白たっぷりのエディトリアル、後半が詰め込みのリファレンス、という無自覚な切り替えは読者のリズムを乱す。密度を変える必然性があるなら（例：前半は背景説明、後半は仕様の逐条整理）、明確な章区切り（罫線＋見出しウェイトの変化）を挟んで切り替えを宣言する。

### 3. 区切りの言語

セクション同士をどう分けるかは、文書のトーンを決める最初の一手になる。

- **ヘアラインルール。** 0.5〜1pxの線。最も汎用的で誠実な既定選択。
- **ネガティブスペース。** 罫線を引かず、余白そのものを区切りにする。エディトリアル度の高い文書に向く。
- **セクション番号。** 「01」「02」のような通し番号。手順書・仕様書など、順序そのものに意味がある文書でのみ使う。
- **見出しウェイトの変化。** 章の切れ目だけ見出しを太く・大きくする。ルール線を増やさずに階層を示せる。
- **ダブルルール。** 上下に近接した2本の線。章の切れ目のような、強い区切りにのみ使う。多用すると文書全体が儀式的に見える。

迷ったら「ヘアラインルール」か「ネガティブスペース」を既定にする。ブリーフが強くエディトリアルなトーンを求めているときだけ、それ以外の選択肢を検討する。

### 4. コールアウト・引用・脚注・コードブロックの扱い

- **コールアウト/補足ボックス。** 左に太めのアクセントバー（3〜4px）＋淡い背景色（`--color-paper-2`程度）で本文と区別する。使いすぎない——目安は300〜500語に1個まで。種類（注意／補足／警告など）を色分けする場合も3種までとし、それ以上は読者が意味の違いを覚えきれない。
- **引用。** `<blockquote>`＋出典の明記をセットにする。出典不明の引用は使わない（数値・実績の捏造禁止という本体の原則と同じ理由）。
- **脚注。** 本文中に上付き番号のアンカーリンクを置き、文書末の脚注リストへ、さらに脚注から本文へ戻るリンクを用意する。学術的な文書、厳密な出典管理が必要な文書でのみ使う。ブログ的な共有文書では、脚注より本文中の直接リンクの方が素直に機能することが多い。
- **コードブロック。** 等幅フォントトークン（例：`--font-mono`）を使い、シンタックスハイライトもトークン化された配色に載せる。ハイライターの既定テーマ（唐突な紫・緑）をそのまま出さない。行番号は特定行を名指しで参照する必要があるときだけ表示する。

### 5. 図解とテキストの比率

- 文章だけで説明が完結するなら図解を足さない。比較対象が3列5行以内、時系列が分岐のない4〜5点以内であれば、Mermaidのflowchartではなく表または箇条書きで足りることが多い。図解の要不要判定の詳細は [`diagram.md`](diagram.md) を参照。
- 図を挟む頻度の目安は800〜1,200語に1点程度。これより高頻度に図が出てくる文書は、文章で語るべき論理展開を安易に図へ逃がしている兆候であることが多い。
- 図・画像の直前直後には短いキャプションまたは説明文を添え、図単体で意味が完結する状態にしない。視覚に強く依存できない読者への配慮でもある。
- 図の配置は本文の測度（`max-width: 65ch`）を超えてよい——図は全幅ブリードにしてよい数少ない要素の一つ。全幅にする場合、前後の余白を広めに取り、「これは本文の流れから一段離れた要素だ」と視覚的に示す。

## スライドの構造軸

### 1. 1スライド1トピックの原則

- 具体的な上限の目安：本文は1スライドあたり40〜60語（日本語なら100〜150字程度）、箇条書きは最大5項目、1項目は1行（折り返しても2行まで）に収める。
- 判定質問：「このスライドを2枚に割っても、それぞれが単独で成立するか？」成立するなら、すでに2つのトピックが1枚に同居している——分割する。
- スライドタイトルは1つの主張を短く言い切る。タイトルだけを読んでスライドの結論が伝わる状態が理想。「〜について」のような無内容なタイトルは避ける。

### 2. 表紙スライド・章区切りスライド

- **表紙。** タイトル＋サブタイトル＋発表者名・日付程度。装飾も本文コンテンツもここには持ち込まない。
- **章区切り（セクションディバイダー）。** 大きな章番号＋章タイトルのみのスライド。本文コンテンツスライドと明確に区別できるビジュアル（背景色の反転、書体サイズの極端な違いなど）にする。10枚を超えるデッキでは、章区切りが聴衆にとって「今どのパートを聞いているか」の手がかりになる。

### 3. スライド間のリズム

- テキスト主体のスライドを3枚以上連続させない。図解・写真・引用スライドを挟んで視覚的な休符を作る。
- 逆に図解ばかりが連続すると、話の骨格（結論・主張）が見えにくくなる。テキストで主張を明言するスライドと、図解でそれを裏付けるスライドを交互に配置するのが基本形。
- デッキ全体で同じレイアウトテンプレート（例：常に左テキスト＋右図解）を機械的に繰り返さない。最低でも2〜3種のレイアウトパターン（全画面見出しのみ／左右分割／中央1点集中／表）を使い分ける。

### 4. 話者ノート

- 話者ノートは聴衆向けのスライド本体とは別要素として持たせる（例：`<aside class="speaker-notes">`）。スライド本体のCSSでは非表示にし（`display: none`）、必要に応じて印刷用スタイル（`@media print`）やノート専用ビューでのみ表示する。
- スライド本体に書き切れなかった背景説明・想定質問への回答・数字の根拠はノート側に逃がす。本体のテキスト量を削る代わりにノートを厚くする、という関係を意識する。本体にノート相当の情報量を詰め込んで1スライド1トピックの原則を破らない。

### 5. 番号・進捗インジケーター

- 8枚を超えるデッキでは、ページ番号（例：隅に小さく`12`）または進捗表示（例：`03 / 12`）を入れる。8枚以下の短いデッキでは省いてよい——聴衆が全体量を目視で把握できるため、あってもなくても迷わない。
- 進捗バー（画面下部の細い線が伸びていく形式）はセミナー・ウェビナーのような長尺デッキに向く。役員会議向けの短い意思決定資料では過剰な演出になりやすく、省く。
- 16:9固定ビューポートを前提にする場合、`aspect-ratio: 16 / 9` のコンテナ＋スクロールスナップ（`scroll-snap-type: y mandatory`）で1画面=1スライドを保証し、スライド内でスクロールが発生しない（コンテンツが枠からあふれない）ことを出力前に確認する。あふれる場合は情報を削るか次のスライドへ分割する——フォントサイズを縮めて枠に押し込むのは、原則1（1スライド1トピック）の上限を超えているサインである。

## フィンガープリントを選ぶ

文書・スライドいずれも、上記の軸から一つずつ選んだ組み合わせが、その成果物の「フィンガープリント」になる。守るべき原則はWebページ制作と同じく一貫性だ——リファレンス的な高密度の文書に、ふんわりした余白多めのコールアウトを頻発させない。テキスト主体のスライドが続く章に、写真1枚だけの静かなスライドを挟むこと自体は良いリズム作りだが、それが全体のトーン（technical / editorial / brutalist 等）と矛盾していないか確認する。

## 文書・スライド共通のアンチパターン

- **H2の羅列だけで階層を作った気になる。** すべての見出しが同じウェイト・同じ余白で並ぶと、文書全体が単調な「見出しスープ」になる。章の重みに応じてウェイトと余白を変える。
- **短い文書に反射的にTOCを付ける。** H2が2〜3個しかない文書にTOCが付くと、内容量に対して仰々しい印象になる。
- **すべてのスライドが同じ箇条書きレイアウト。** タイトル＋5項目の箇条書き、という型を全スライドで繰り返すと、内容に関わらず同じテンプレートを流し込んだように見える。
- **枠に収まらない情報をフォントサイズで押し込む。** スライドがあふれかけたときにテキストを小さくして帳尻を合わせるのは、情報過多を隠しているだけで解決していない。
- **話者ノートが聴衆向けビューに漏れている。** 発表時に地の文の背景説明がそのまま画面に映ってしまうのは、要素を分離できていない実装ミス。
- **段落ごとにコールアウトボックスを置く。** 補足を強調したい気持ちが先行し、ページ全体が色付きボックスだらけになると、どれも強調されていないのと同じになる。

## 迷ったとき

ブリーフに構造の手がかりがなく方向性も定まっていない場合は、なんとなくの既定に流されないこと。内容のドメイン（技術仕様、意思決定の背景説明、研修資料、社外向け説明会など）を読み取り、そのドメインに合いそうな構造的アプローチを2〜3案、性質の異なる方向性で考えてから提案する。密度の異なる案（リファレンス主導／エディトリアル主導）、あるいは形式そのものが異なる案（文書主導／スライド主導）を並べることで初めて対比が生まれる。似た案を3つ並べるのは、このファイルが解消しようとしている画一性の一種でしかない。

ドメインの手がかりが読み取れない場合は「これは誰が、どんな場面で読む/見るものですか」と一つだけ質問し、それを踏まえて構造の方向性を絞り込む。ユーザーが「わかりやすく」「きれいに」のような曖昧なトーン語で答えた場合、それは具体的な手がかりにならない。用途や読み手について改めて尋ね直す。
