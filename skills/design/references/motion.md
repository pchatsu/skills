# モーション

AI生成のモーションはとかく散漫になりがちである。すべての要素にホバーリフト、すべてのスクロールでフェードイン、跳ねるアイコン。それを鎮める。小さなモーションを10個入れるより、1つのオーケストレーションされた瞬間のほうが強い。この原則は、Webアプリのマイクロインタラクションだけでなく、長文ドキュメントのスクロールリビールやスライドの遷移にも同じように適用される。

## 原則

- **アニメーションさせるのは`transform`と`opacity`だけ。** この2つはGPUで合成されレイアウトを発生させない。それ以外のプロパティはパフォーマンスの問題につながりやすい。
- **長さは3段階に分ける。** Micro（100〜150ms）、minor（200〜300ms）、major（300〜500ms）。退出は入場の約75%の長さにする。
- **イージングは指数関数的なease-outを使う。** 入ってくる要素は減速しながら着地する。出ていく要素は加速しながら離れる。
- **モーションは意味を伝えるためにある。** そのトランジションが何を伝えているのか説明できないなら、削る。
- **reduced motionへの対応は必須。** `@media (prefers-reduced-motion: reduce)` で、空間的な動きはすべてopacityのクロスフェードに畳み込む。

## イージング

以下の3種類のみを使い、トークンとして名前をつける。

```css
:root {
  --ease-out: cubic-bezier(0.16, 1, 0.3, 1);        /* 入ってくる要素 */
  --ease-in:  cubic-bezier(0.7,  0, 0.84, 0);       /* 出ていく要素   */
  --ease-in-out: cubic-bezier(0.65, 0, 0.35, 1);    /* 状態のトグル   */
}
```

`ease`、`ease-in-out`（ブラウザのデフォルト）、`cubic-bezier(0.25, 0.1, 0.25, 1)` はいずれもブラウザの初期値であり、作り込まれていない印象を与える。

## 長さ

```css
:root {
  --dur-micro: 120ms;   /* ボタン押下、トグル切り替え、色の変化、ホバー遷移、フォーカスリング */
  --dur-short: 220ms;   /* ツールチップ、アコーディオン開閉、スライド遷移 */
  --dur-long:  420ms;   /* モーダル、ドロワー、ページの表示 */
}
```

退出時は入場の75%程度の長さにする。

```css
.menu.is-open  { transition: transform var(--dur-short) var(--ease-out); }
.menu.is-close { transition: transform calc(var(--dur-short) * 0.75) var(--ease-in); }
```

## ページ読み込み時のオーケストレーション

ページ読み込み時のシーケンスは1つにまとめる。DOMの順序に応じたスタガー（ずらし）は、JSではなくCSSのカスタムプロパティで行う。

```html
<section style="--i: 0">…</section>
<section style="--i: 1">…</section>
<section style="--i: 2">…</section>
```

```css
.reveal {
  opacity: 0;
  transform: translateY(8px);
  animation: reveal var(--dur-long) var(--ease-out) forwards;
  animation-delay: calc(var(--i, 0) * 60ms);
}
@keyframes reveal {
  to { opacity: 1; transform: none; }
}
```

スタガーの合計は約500msを上限とする。それを超えるとページの表示が遅く感じられる。

## スライドの遷移

プレゼンテーション（1画面=1トピック、16:9固定ビューポート）では、遷移そのものを主役にしない。読者の注意は、遷移の演出ではなく次のスライドの内容に向かわせる。

- **基本はフェード、または単純なカット。** スライドが切り替わる瞬間、直前のスライドをフェードアウトさせながら次をフェードインさせる（クロスフェード）か、演出なしで即座に切り替える（カット）。どちらも「読む」体験を妨げない。
- **3D回転、キューブ、ページめくり、パースの効いたスライドインは避ける。** これらは登壇者が操作する物理的なプレゼンツールの演出をWeb上で再現しようとする過剰なギミックであり、内容ではなく遷移そのものに注意を引いてしまう。
- **遷移時間は`--dur-short`（220ms）を基準にする。** これより長いと「待たされている」感覚が生まれ、聴衆が次のスライドの内容に入る前にタイムロスが積み重なる。
- タイトルや図版など、スライドをまたいで同じ要素が連続する場合に限り、控えめな`transform`のクロスフェードで連続性を示してもよい。ただし全スライドに適用する既定演出にはしない——効果があるのは「ここで何かがつながっている」と示したい特定の瞬間だけである。
- スライド内の要素（箇条書きなど）を1つずつ出す「ビルド」演出を使う場合も、上のページ読み込みオーケストレーションと同じスタガーの発想を流用してよいが、合計時間を長引かせない。

## 長文ドキュメントでのスクロールリビール

- `scroll`イベントリスナーではなく、必ずIntersectionObserverを使う。
- 用途は「一度だけ出現させる」控えめなフェードイン／フェードアップ（`opacity: 0 → 1` ＋ `translateY(8px) → 0`程度）に限定する。パララックスは使わない。明確な理由がない限りスクロール連動でスクラブするアニメーションも使わない。
- **使いすぎない。** 長文の主目的は読むことである。本文の段落1つひとつ、リストの項目1つひとつにリビールを付けると、読者はスクロールするたびに視線を奪われ、読書のリズムが途切れる。リビールは見出し単位・セクション単位など、粒度の粗い区切りにとどめる。
- 表・コードブロック・引用など、内容を正確に参照したい要素にはリビールを使わない。読者が読み返そうとスクロールを戻した瞬間に再アニメーションして気が散る、といった事故を避ける。
- スクロールトリガーのモーションには必ずreduced-motion用のフォールバックを用意する。

## 状態遷移（Webアプリ）

ボタンのホバー、メニューの開閉、モーダル、アコーディオンといったWebアプリのマイクロインタラクションは、上記のduration・イージングの原則をそのまま使う。具体的な振り付け（ホバー時の`translateY`量、モーダルのスケール値、popover APIの使い方など）は [`microinteractions.md`](microinteractions.md) を参照する。

## Reduced motion

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 150ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 150ms !important;
  }
  .reveal { animation: reveal-reduced 150ms linear forwards; }
  @keyframes reveal-reduced { to { opacity: 1; transform: none; } }
}
```

プログレスバーやローディングスピナー、スケルトンなど、機能的な意味を持つモーションは動かし続けてよい。速度を落とすだけにする。スライドの遷移も、reduced motion時はフェードをカットに畳み込む。

## 禁則事項

- `ease`（ブラウザのデフォルト、平凡な印象になる）。
- プログレスバーや点滅するローダー以外での`linear`。
- UI要素へのバウンス／エラスティック／オーバーシュート。古臭く、「テンプレート感」を与える。
- `width`、`height`、`top`、`left`、`margin`、`padding`をアニメーションさせる。
- クラス全体に事前設定された`will-change`。要素単位で、実際にアニメーションしている間だけ設定する。
- パララックス。
- カスタムカーソル。
- reduced-motionのフォールバックを伴わないスクロール駆動アニメーション。
- 機能的なローダー以外の無限ループ。視線を引きつけたまま離さない。
- スライドの3D回転・キューブ・ページめくりなどのギミック的な遷移。
- 長文ドキュメントの段落単位・リスト項目単位でのスクロールリビールの乱用。
