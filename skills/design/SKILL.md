# design

汎用のAIコーディングアシスタント向けデザインスキル。目的はただひとつ、生成した文書やスライドが「AIが作った感じ」に見えないようにすること。

対象は、自分用の理解ノート・共有用の文書・プレゼンテーション資料といった、1ページ完結のHTML成果物。マーケティングのランディングページやWebアプリのUIは対象外。

このスキルは意図的に短く、意図的に頑固です。狙いは「視覚的なバリエーション」ではなく「構造的なバリエーション」です。同じブリーフから何度作っても、色を変えただけの同じテンプレートにはしません。毎回、そのブリーフのために配色・タイポグラフィ・構造を原則から組み立てます。固定のテーマ集やレイアウト集は持ちません — 選択肢を用意するのではなく、判断のしかたを示すことがこのスキルの中心です。

## 適用範囲

このスキルは、**自分用の理解ノート・共有用の文書・プレゼンテーション資料**といった、1ページ完結のHTML成果物を作る/整える依頼全般に適用します。成果物の形は主に2種類です。

- **ドキュメント形式** — 上から下にスクロールして読む長文の1ページHTML。ノート、リファレンス、共有用の資料など。
- **スライド形式** — 1画面=1トピックで区切られたプレゼンテーション。16:9などの固定ビューポートを前提とし、多くの場合ブラウザの印刷機能でPDF書き出しもする。

どちらを選ぶか（あるいは両方を組み合わせるか）は Step 1 のコンテキストゲートで決める。マーケティングのヒーロー・ナビゲーションバー・フッター・CTAボタン・価格表・テスティモニアルといった、Webサイトの営業的な構成要素はこのスキルの対象外。

3つの動作があります。

| 呼び出し | 内容 |
| --- | --- |
| *(デフォルト)* | ユーザーが新しく文書またはプレゼンテーションを作ってほしいと頼んでいる。下記「デザインフロー」に従う。 |
| `redesign <対象>` | 既存の文書/スライドを、中身（内容・情報設計）は保ったまま視覚的な構造だけ作り直す。[`references/verbs/redesign.md`](references/verbs/redesign.md) を読み込んで従う。 |
| `study <スクリーンショット \| URL>` | ユーザーが手本にしたい資料の画像またはURLを渡してきた。ピクセル単位の模写はせず、構造・配色・タイポグラフィの「DNA」を診断して報告する。[`references/verbs/study.md`](references/verbs/study.md) を読み込んで従う。 |

どちらの動詞にも明確に当てはまらない依頼はデフォルト（新規構築）として扱う。ユーザーが画像やURLを動詞なしで貼っただけの場合は一度だけ聞く：「これは参考として `study`（DNA抽出）しますか、それとも新規構築の着想元として扱いますか？」

**実装への配慮。** 本スキルはデザインの規律であって、既存コードベースを壊してよい許可証ではない。既存プロジェクトの一部として文書/スライドを追加・改修する場合：
- 本番ファイル・既存の資料・関連コンポーネントを、ユーザーが明示的に削除を依頼するか、削除箇所を列挙した計画を承認しない限り削除しない。
- 名指しされたファイルのその場編集、または既存の構成に正しく組み込まれる追加ファイルを基本とする。複数ファイルの削除が必要な作り直しなら、先に確認を取る。
- PDF・README・`.md`のブリーフ・議事録・元資料は参考資料として扱う。ユーザーが明示的に「そのまま使って」と言わない限り、一字一句をページにコピーしない。
- 編集前に、変更/新規作成/削除するファイルを明言する。削除には明示的な確認が必須。

## どの verb でも通底する規律

以下の6つは verb 固有ではない。デフォルトのデザインフロー・`redesign`・`study` すべてに共通して適用する。

1. **出力前の自己採点。** 出力を渡す前に、Philosophy（哲学）・Hierarchy（階層）・Execution（実装）・Specificity（具体性）・Restraint（抑制）の5軸で1〜5点をつける。3点未満の軸があれば、渡す前に作り直す。成果物の先頭にスコアをコメントで残す（例：`/* design · pre-emit critique: P5 H4 E5 S4 R5 */`）。詳細は [`references/slop-test.md`](references/slop-test.md) 「出力前の自己採点」を参照。

2. **正直なコピー — 数値・実績の捏造禁止。** ユーザーが数値やデータを渡していないなら、それを発明しない。*「+47% 改善」* *「50,000社以上が導入」* のような発明された数字はその瞬間にAI臭さになる。対処法の詳細は [`references/copy.md`](references/copy.md) の「誠実なコピー」を参照。

3. **トークンを固定し、途中で即興しない。** 配色・フォントの方針を決めたら、成果物内のすべての色と `font-family` は名前付きトークン（`var(--color-accent)`、`font-family: var(--font-display)`）を経由する。生の OKLCH / hex / `rgb()` や、トークンを迂回する `font-family: "Some Font"` は禁止。新しい値が必要になったら、まずトークンブロックに名前付き変数として追加してから参照する。

4. **描き直したUIクロームを作らない。** 偽のブラウザバー（URLピル＋信号機ドット）、偽のスマホフレーム、偽のコードウィンドウ（タイトルバー＋ドット付き `<pre>`）、偽のIDEクロームを手作りしない。スクリーンショットを埋め込む場合はユーザーの環境がすでに本物のクロームを提供している。実際のスクリーンショットを `<figure>`（枠線は細い線1本まで）で使うか、クロームなしでコンテンツ自体を主役にする。

5. **形式に応じた表示保証。** ドキュメント形式ならスマホでもPCでも横スクロールなく快適に読める（`overflow-x: clip`、`minmax(0, 1fr)`、長い単語の折り返しなど）。スライド形式なら固定ビューポート内にテキストが収まり、部屋の後ろからでも読める大きさ・コントラストを保つ。詳細は [`references/responsive.md`](references/responsive.md)。これは努力目標ではなく最低ライン。

6. **タイポグラフィの純度 — 見出しにイタリック禁止。** 見出しとディスプレイ書体は常にローマン体（`font-style: normal`）。地の文の見出しの中に強調用のイタリック単語を混ぜる（`Built to <em>think</em>`）のは最も見破られやすいAIの癖のひとつ。強調はウェイト・アクセントカラー・下線で表現する。イタリックは本文中の引用・強調としてのみ許可する。

## デザインフロー（デフォルト）

### 0. プリフライトスキャン

既存プロジェクトの一部として作業するなら（`package.json`、CSS、既存の資料ファイル等がある場合）、ユーザーに何も聞く前にまず読む。すでにある配色やフォントを無視して壊してしまうと、このスキルを使い続けてもらえなくなる。単発のスクラッチファイルとして作る場合はこのステップは自然に発生しない。

**確認する信号源：**
1. **フォントスタック** — `next/font`、`@fontsource/*`、Google Fonts の `<link>`、`tailwind.config` の `fontFamily`、CSS の `@import url("fonts.googleapis.com/...")`
2. **パレット** — `:root` 内の OKLCH/HSL/hex、`tailwind.config` の `colors`、`tokens.json` 等のデザイントークンファイル
3. **既存の文書/スライドの慣習** — 同じプロジェクト内に他のノートやスライドがあれば、見出しスタイル・図解の描き方・スペーシングの慣習を確認する
4. **スペーシングスケール** — CSS の `--space-*` パターン、4pt/8ptスケールの有無
5. **フレームワーク** — 素のHTML／静的サイトジェネレータ／その他

**出力形式** — Step 1 の前に一度だけ、ファイル:行番号付きでこのブロックを出す：

```
プリフライト調査結果：
・フォント: Geist + Geist Mono（next/font, package.json L23）
・パレット: OKLCH カスタムプロパティ（app/globals.css :root）
・スペーシング: CSS --space-*（4ptスケール, styles.css L18）
・既存資料: notes/2026-03-slides.html と見出しスタイル・配色を共有可能

このスキルが維持するもの: フォントスタック、パレット、スペーシングスケール
このスキルが新たに導入するもの: 構造の規律・図解の作法・出力前チェック

既存の要素を上書きしてほしい場合はその旨を伝えてください。
```

既存の信号が何も見つからない（新規のスクラッチファイル、空プロジェクト）場合は一言だけ：*「プリフライト信号なし — 標準の規律一式で進めます。」* 矛盾する信号を見つけたら明示的に指摘し、どちらを優先するか確認を取る。ユーザーが「既存は無視して」と言った場合はプリフライトを飛ばし、その旨を一言だけ伝えて Step 1 へ進む。

### 1. デザインコンテキストゲート

コードを書く前に、3つを把握する。

1. **用途** — 自分の理解のためのメモ・誰かに共有する資料・人前で話すプレゼンテーションのどれに近いか（複数の性格が混ざっていても構わない）。
2. **ゴール** — これを読んだ／見た人に、どうなっていてほしいか（理解する、判断材料にする、納得して行動してもらう、など）。
3. **トーン** — 極端さを選ぶ。*editorial（編集的）・brutalist（ブルータル）・soft（ソフト）・utilitarian（実用一辺倒）・luxury（高級）・playful（遊び心）・technical（技術的）・austere（禁欲的）* のいずれか。「クリーンでモダン」はトーンではない。

**常に聞く — 答えるかどうかはユーザーの自由。** ブリーフがどれだけ簡潔でも（*「この設計の説明ノートを作って」*のような短いブリーフでも）必ず一度だけ聞く。むしろ短いブリーフほど、モデルが勝手に補完したくなる場面なので聞く価値が高い。

質問フォーマット：

> *作る前に3つ教えてください。*
>
> *1. **用途** — 自分の理解のためのメモ・誰かに共有する資料・人前で話すプレゼンテーションのどれに近いですか？*
> *2. **ゴール** — これを読んだ／見た人に、どうなっていてほしいですか？（理解する・判断材料にする・納得して動いてもらう、など）*
> *3. **トーン** — 極端さを選んでください：editorial・brutalist・soft・utilitarian・luxury・playful・technical・austere。「クリーンでモダン」はトーンになりません。*
>
> *あるいは「そのまま進めて」と言っていただければ、ブリーフから推測して進め、何を選んだか報告します。*

一度のメッセージで送る。ユーザーが一部だけ答えて残りを飛ばしたら、飛ばした項目は推測してよい。ユーザーが「そのまま進めて」「任せる」「聞かないで」と言った、または反応がなかった場合は、以下の推測プロトコルに従う。

**形式（ドキュメントかスライドか）の判断。** 用途の回答から自動的に決める — 自分用メモ・共有用文書はスクロール型ドキュメント、プレゼンテーションはスライド形式（固定ビューポート）をデフォルトとする。ブリーフから読み取れない、または両方の性格が混ざる場合は一言確認する：*「読み物として上から読むドキュメント形式にしますか、それとも1画面1トピックのスライド形式にしますか？」* 決まったら一文で明示する：*「形式：スライド（16:9）」*。

**例外** — `redesign` や `study` として呼ばれた場合はこのゲートを飛ばす（対象そのものからコンテキストを読むため）。

**ユーザーが聞かれるのを拒否・スキップした場合：**
- ブリーフ・ドメイン・見えているコンテキスト（ファイル名、周辺資料）から用途・ゴール・トーンを推測する。
- 返信の冒頭で一文にまとめて明示する：*「用途＝X・ゴール＝Y・トーン＝Zで進めます。違っていたら教えてください。」*
- この推測を Step 6 のスタンプコメントにも残す。

推測を黙って進めることは絶対にしない。ユーザーが何を推測されたか見えなければ、間違っていても修正できない。

3つが定まったら（聞いた上でも推測でも）、一文で確認してから先に進む。

### 2. 構造とボイスを決める

固定のテンプレート集は使わない。代わりに、[`references/structure.md`](references/structure.md) にある構造の軸（ドキュメントなら見出し階層・目次の要否・セクションのペース配分・コールアウトの扱い、スライドなら1スライド1トピックの原則・表紙と章区切りの扱い・スライド間のリズム）を、このブリーフのために意識的に選ぶ。

**やってはいけないのは、毎回同じ構成に逃げること。** 長文の理解ノートと、人前で話すプレゼンテーションでは、情報密度もペース配分もまったく違う。ブリーフの用途とトーンに応じて、見出しの配置・セクション/スライドの並べ方を都度選び直す。

コードを書く前に、選んだ構造を一文で言葉にする：*「構造：見出し3階層＋目次あり、コールアウトboxで補足を分離、区切りは太い罫線1本。」*（スライドの場合の例：*「構造：全12枚、表紙1・章区切り3・本編8、1枚1トピックを厳守。」*）

### 3. ビジュアルルールセットを読み込む

原則は [`references/`](references/) にある。

**毎回読む：**
- [`typography.md`](references/typography.md) — フォント、スケール、ペアリング、見出し/タイトルサイズの決め方
- [`color.md`](references/color.md) — OKLCH、パレットの組み立て方、アクセントの節度
- [`layout-and-space.md`](references/layout-and-space.md) — 4ptスケール、グリッドの崩し方、非対称性、奥行き
- [`motion.md`](references/motion.md) — duration、イージング、何をアニメーションさせるべきか、reduced-motion対応
- [`copy.md`](references/copy.md) — 見出し・本文・キャプションの書き方、誠実なコピーの原則
- [`anti-patterns.md`](references/anti-patterns.md) — 名指しで避けるべきAIの癖
- [`responsive.md`](references/responsive.md) — Step 1で選んだ形式に応じて範囲を絞って読む。ドキュメントなら「A. 文書」節、スライドなら「B. プレゼンテーション」節だけでよい

**条件付きで読む（本当に必要なときだけ。念のための先読みはしない）：**
- [`diagram.md`](references/diagram.md) — フローチャート・比較・時系列・関係性などの図解が必要かどうか迷うとき、または実際に図解を作るとき（Step 4 参照）
- [`microinteractions.md`](references/microinteractions.md) — 目次リンク・折りたたみセクション・コピーボタン・スライドナビゲーションなど、何らかのインタラクティブ要素があるとき
- [`interaction-and-states.md`](references/interaction-and-states.md) — 上記のインタラクティブ要素が状態（読み込み中・成功・無効など）を持つとき

**最後に読む：**
- [`slop-test.md`](references/slop-test.md) — Step 6（出力前チェック）で初めて開く。生成前の参考資料ではなく、出力後の検査ゲート。
- [`contract.md`](references/contract.md) — 引き渡し時の出力契約とスコープのルール

### 4. 図解を決める

多くの文書・スライドは図解を必要としない。見出しと文章の構造だけで十分伝わることも多い。ブリーフの内容が比較・フロー・時系列・関係性を含む場合だけ [`references/diagram.md`](references/diagram.md) を開く。

そのファイルにある「そもそも図解が必要か」の判定（3列5行程度の比較なら素のHTML表で足りる、時系列は簡単な箇条書きで足りることも多い）と、Mermaidを使う場合のスタイリング規律（デフォルトテーマのまま出さない、ページの配色トークンに合わせる、ノード数と複雑さの上限）に従う。実在しないデータをでっち上げて図解の中身にしない。

判断を一文で言葉にする（例：*「図解：なし — 文章構成のみ」* または *「図解：Mermaid flowchart 1点（処理の流れ）、ページ配色に合わせたカスタムテーマ」*）。

### 5. プレビュー

コードを書く前に、これから出すものの要約を出す。ユーザーが5秒で読んで、大量のコードを書く前に軌道修正できるようにするため。

```markdown
**design**

- **形式** · スクロール型ドキュメント（全5セクション）
- **構造** · 目次あり、見出し3階層、コールアウトboxで補足を分離
- **配色・書体** · 紙色 oklch(98% 0.01 90) を基調にインクブルーのアクセント／見出しは高コントラストセリフ＋本文はグロテスクサンス
- **図解** · Mermaid flowchart 1点、ページ配色に合わせたカスタムテーマ
- **モーション** · スクロールでの控えめなフェードイン
- **出力前チェック** · 通過（Step 6 で実施）
```

スライド形式なら「形式」「構造」を枚数・章構成に置き換える。

### 6. ビルド

用途とトーンに見合ったコードを出す。

常に：
- **見出し/タイトルはtypography.mdの基準に従う。** ドキュメントなら文書見出しスケール（H1〜H4のモジュラースケール）、スライドならスライドタイトルサイズ（遠くからでも読める大きさ）に従う。
- **セクションタグ/アイキャッチはデフォルトOFF。** `01 · SECTION` のような大文字モノスペースの通し番号ラベルは、ユーザーが明示的に頼んだか、内容が本当に順序性を持つときだけ使う。使うときも1ページに1〜2箇所まで。タグを使うなら必ず縦積み（タグの直下に見出し）にする——タグを見出しの左マージンに置く2カラムパターンは最もテンプレっぽく見える型なので禁止。
- すべての色に OKLCH を使い、`:root` にCSSカスタムプロパティとしてトークン宣言する。
- 意味のある名前をつけた4ptスペーシングスケール（`--space-sm`、`--space-md`…）を使う。
- 個性のあるディスプレイ書体と、読みやすい本文書体を組み合わせる。単一書体そのものが狙いである場合（本物のターミナル風ページなど）を除き、1書体だけで済ませない。
- 目次リンク・折りたたみ・コピーボタン・スライドナビゲーションなど実際にあるインタラクティブ要素は、[`interaction-and-states.md`](references/interaction-and-states.md) に従って必要な状態（default・hover・focus-visible・active・disabled等、要素に応じて）を設計する。
- `transform` と `opacity` だけをアニメーションさせる。レイアウトプロパティは触らない。
- 名前付きイージング（`--ease-out`、`--ease-in`、`--ease-in-out`）を使う。ブラウザデフォルトの `ease` や、バウンス/オーバーシュートは使わない。
- `prefers-reduced-motion: reduce` に対応する。空間的な動きは150ms以下のopacityクロスフェードに縮退させる。
- `:focus-visible` にコントラスト比3:1以上の可視リングを設定する。リングの出現自体はアニメーションさせない（フォーカス時に即座に表示する）。
- **長いドキュメントには目次を検討する。** 一定の長さを超えたら [`structure.md`](references/structure.md) の基準に従い目次(TOC)を付けるか判断する。**スライドは固定ビューポートに収まっているか確認する。** [`responsive.md`](references/responsive.md) の基準（文字サイズ・コントラスト・オーバーフロー）を満たす。
- **成果物にスタンプを残す。** 生成したCSSファイル（またはインラインの `<style>`）の先頭行に、コメントで `/* design · 形式: <ドキュメント|スライド> · 構造: <一言> · トーン: <トーン> */` を残す。これは何を選んだかの記録であり、同一セッション内で次に作る際の多様性判断の材料になる。
- **既存のグローバルスタイルシートを壊さない。** すでにエントリーのスタイルシートがある場合は追記のみ。ユーザーが明示的に上書きを求めない限り、ファイル全体を書き換えない。
- **トークンを1箇所にまとめる。** 使用した `--color-*`・`--font-*`・`--space-*`・`--text-*`・`--ease-*`・`--dur-*`・`--radius-*` トークンは、ページCSS（または既存スタイルシート）の `:root` に集約して宣言する。生の値を本文中に直接埋め込まない。

### 7. 出力前チェック（slop test）

引き渡す前に、[`references/slop-test.md`](references/slop-test.md) のチェックリストで出力を検査する。このファイルはこの段階で初めて開く。どの問いにも「いいえ」でなければならない。1つでも引っかかったら該当のBuildステップに戻って直し、Step 5 のプレビューを訂正版で出し直す。
